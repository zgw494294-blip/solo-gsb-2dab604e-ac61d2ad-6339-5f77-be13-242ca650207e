# 木料定尺裁切（Cut Stock Optimizer）

基于 **Flask + 原生 JavaScript** 的一维木料定尺裁切 Web 应用。输入原板长度、单价、
可用数量、所需零件（长度 × 件数）与锯缝宽度，求解覆盖全部零件的**全局最优方案**：

1. **原板总价最低**（所有原板单价相同，即使用原板数量最少）；
2. 板数相同的方案中，**各板余料之和最短**；
3. 不存在可行方案时，页面明确给出无解原因（如零件超长、容量/数量不足）。

页面逐板列出切件尺寸、锯缝道数与合计、占用长度、余料，以及合计价格。

此外支持**多订单合板费用分摊**：录入 2～4 个订单（名称 + 各自的零件清单），
沿用同一组原板参数合板裁切，按 **Shapley 值**把合板最优总价公平分摊到每个订单，
页面展示合板总价、各单精确分摊值（分数）与最终应付金额（精确到分）。

还支持**锯机作业排程**：单份清单排料后，录入统一的每板准备分钟与 2～4 台锯机
（各自的最早可用分钟、每件切割分钟），把每块原板作为不可拆分作业分配到锯机，
**精确最小化已接单机台的最晚完工分钟**（未分配原板的闲置机台不计入），
并列时取按原板编号排列的机台编号序列字典序最小者，
页面逐机列出各原板的开工、完工分钟及整体完工分钟。

另有**裁切执行核销**模块：用单份清单参数在服务端求解，可行时把输入与逐板方案
**冻结到 SQLite** 成为一个核销批次（版本从 0 开始，各板初始「待加工」），无解不建批次。
之后可按批次 ID 打开批次，逐板提交核销结果（每板仅可从「待加工」转为「合格」或
「报废」）；上报携带**幂等键**与**期望版本**，成功时原子更新所有板并把版本加一，
同键同载荷的重试直接返回首次保存的响应。页面显示各长度的合格件数与待加工、
报废板数。

批次还支持**实测尺寸复核**：打开批次后，可为已核销为「合格」原板的切件填写
实测长度（正整数）并输入非负整数公差，未录入的切件不参与本次复核。复核为只读
预览，不修改批次。冻结需求按零件录入顺序展开为单件，实测件仅可分给长度差绝对值
不超过公差的需求件、每件需求至多使用一次，按「满足件数最多 → 总长度偏差最小 →
按板号与切件序号排列实测件后需求件序号序列字典序最小（未分配排最后）」精确求解，
页面展示逐件去向、未分配实测件与各需求长度的缺件数。

批次另支持**合格切件错缝拼板预览**：在批次页面勾选 1～10 件已核销合格板的切件
（以板号＋切件序号标识），设定正整数目标行长、2～4 行与非负整数最小错缝距离。
按等宽木条、接头无长度损耗计算且不裁短：每行切件长度之和恰等于目标行长，每件
最多用一次，允许余件；接缝位置为除末件外的累计长度，相邻行任意两接缝位置差的
绝对值须不小于错缝距离（无接缝行不限制邻行）。精确求用件数最少的可行排布，
并列时逐行比较切件标识序列取字典序最小（先比板号再比切件号，短前缀在前）。
预览为只读，不修改批次；页面逐行展示切件顺序、接缝坐标与未用切件，无解时明确
提示原因。

另有**跨批次合格切件发料单**：按批次 ID 收集 1～10 件切件（每件以
「批次 ID＋板号＋切件序号」标识，可跨批次），填写非空用途与幂等键后提交。
服务端在一笔 SQLite 事务中核对所有切件确属已核销合格板、尚未发料且单内不重复；
任一件无效或已发料整单不写入（已发料返回 409）。成功后冻结切件长度与归属，
生成持久化发料单，切件不得再发料。同一幂等键＋同一用途＋同一选件集合的重试
返回原单（选件顺序不影响比较），同键异载荷返回 409。批次页标注已发料切件，
拼板预览拒绝选用已发料切件。

## 约束规则

| 输入项 | 规则 |
| --- | --- |
| 原板长度、单价、可用数量 | 正整数 |
| 零件长度、零件件数 | 正整数 |
| 锯缝宽度 | 非负整数（允许 0） |
| 需求总件数 | 不超过 12 件（多订单时为全部订单合计） |
| 订单数量（分摊模式） | 2～4 个，每单名称非空、零件清单非空 |
| 锯机数量（排程模式） | 2～4 台，机台按录入顺序从 1 编号 |
| 每板准备分钟、最早可用分钟 | 非负整数（允许 0） |
| 每件切割分钟 | 正整数 |

每块原板切出 n 件时，占用长度为

```
sum(零件长度) + (n - 1) × 锯缝宽度 ≤ 原板长度
```

求解器把问题转化为经典一维装箱问题（件重 = 件长 + 锯缝，箱容 = 板长 + 锯缝），
用带对称剪枝的 DFS **精确枚举**，保证全局最优而非贪心近似。

## 锯机作业排程

排程算法（`schedule.py`）沿用 `/api/solve` 的全局最优裁切结果，把每块原板视为
**不可拆分作业**：

* 原板 b 在机器 j 上的耗时为
  `准备分钟 + 本板切件数 × 机器 j 每件切割分钟`；
* 同一台机器按**原板编号顺序** 1, 2, … 连续加工：首块自该机最早可用分钟起，
  后续各块紧接前一块完工，板间不强制留等待；
* 目标为**已接单机台**（至少分到一块原板的机器）**最晚完工分钟（makespan）
  最小**；未分配原板的闲置机台不计入整体完工时间，其最早可用分钟再晚也不
  影响工期；
* 最晚完工并列时，取“按原板编号顺序排列的机台编号序列”**字典序最小**的分配
  （等价于尽量把小编号原板分给小编号机台）。

原板数不超过 12、机台不超过 4 台，求解器对 `机台数^原板数` 种分配做逐板 DFS
**精确枚举**，并配合同构机台对称剪枝、到达状态记忆与工作量下界剪枝，保证全局
最优；页面按机台逐块展示开工/完工分钟，闲置机台标注“未分配原板”，且不参与
整体完工分钟的计算。排料无解时直接返回无解原因，不生成排程。

## 多订单合板费用分摊

分摊算法（`allocate.py`）：

1. **子集费用**：对 2～4 个订单的每个子集精确求解合板最低原板总价
   （子集内零件合并后求全局最优裁切，费用 = 原板数 × 单价）；空集费用为 0；
2. **Shapley 分摊值**：遍历全部 n! 种订单加入次序，取每个订单边际费用
   `c(S∪{i}) − c(S)` 的平均值，全程用有理数（`fractions.Fraction`）精确计算；
3. **取整到分**：精确分摊值换算为分后，先逐单**向下取整**，剩余的分按
   **小数余数降序**逐个补足（余数相同按订单录入顺序），保证各单应付之和
   恰好等于合板最优总价。

全部订单合板无解时，接口返回无解原因，不生成分摊。

## 裁切执行核销

核销模块（`batches.py`）把一次可行求解冻结为**批次**，并跟踪逐板执行结果：

* **冻结**：`POST /api/batches` 用与 `/api/solve` 相同的单清单参数在服务端求解，
  可行时把输入与逐板方案写入 SQLite（批次版本 0，各板「待加工」）；无解不建批次；
* **状态机**：每板仅可从「待加工」转为「合格」或「报废」，已核销板不可再改；
* **上报**：`POST /api/batches/{id}/reports` 携带非空幂等键、期望版本与非空
  逐板结果；期望版本与当前版本一致且所报板均待加工时，**在单个事务里**原子
  更新所有板、版本加一并保存本次响应；
* **幂等**：同批次同键同载荷的重试直接返回首次保存的响应（不再校验期望版本，
  即忽略旧版本）；结果列表的顺序不影响载荷比较（按板号排序后规范化）；
* **冲突（409，整批不写入）**：期望版本过期、上报已核销板、同键异载荷；
* **持久化**：数据库文件默认位于 `data/batches.db`（可用环境变量 `DB_PATH`
  覆盖），应用启动时自动建目录、建表（幂等，含发料单 `dispatches` /
  `dispatch_items` 表）；Docker Compose 把 `data/` 挂载到命名卷，容器重建后
  批次、核销与发料记录保留。

页面「执行核销」页签可创建批次、按 ID 打开批次并提交核销，实时显示各长度的
合格件数与待加工、合格、报废板数。

## 批次实测尺寸复核

批次存在「合格」原板后，可在批次页面填写各合格板切件的**实测长度**（正整数，
留空的切件不参与复核）与统一的**非负整数公差**，调用
`POST /api/batches/{id}/quality-preview`。接口**只读取**冻结需求与当前板状态，
不写入、不改版本：

* **拒绝（HTTP 400）**：公差不是非负整数；记录不是对象；`board_no`、`cut_no`
  不是正整数或 `actual_length` 不是正整数；同一（板号, 切件序号）重复录入；
  板号不属于批次；板为「待加工」或「报废」；切件序号超出该板切件数；
  批次不存在返回 404；
* **展开**：冻结零件按录入顺序展开为需求单件（从 1 开始连续编号，同一零件的
  多件连续排列）；
* **可行边**：实测件只能分给 `|实测长度 − 需求长度| ≤ 公差` 的需求件，每件
  需求至多被一件实测占用，未匹配的实测件记为**未分配**；
* **精确求解（`quality.py`，分支定界）**：

  1. 满足（匹配）件数最多；
  2. 件数相同的方案中，总长度偏差（`|实测 − 需求|` 之和）最小；
  3. 仍并列时，把实测件按板号、切件序号排列，取其需求件序号序列**字典序最小**
     者，未分配排在任何序号之后。

  每个搜索节点先用 Kuhn 增广求剩余二分图的最大匹配件数上界，再用子集 DP 精确
  求出剩余实测件在空闲需求件上的（最大件数, 最小偏差），配合作业树的字典序前缀
  剪枝，保证全局最优。
* **响应**：返回公差、需求件总数、已录实测件数、满足件数、未分配件数、总偏差、
  按板号/切件序号排列的逐件去向（`assignments`，含计划长度、实测长度、分到的
  需求件序号/长度与单件偏差，未分配时对应字段为 `null`/`assigned=false`）、
  未分配实测件列表（`unassigned`），以及按冻结零件录入顺序给出的各需求长度
  **缺件数**（`shortages`：需求件数 − 已满足件数）。

页面在「执行核销」页签的批次详情中提供复核表单与结果区：需求件编号、逐件去向
表格、未分配实测件标签与各长度缺件数一览。

## 批次合格切件错缝拼板预览

批次存在「合格」原板后，可在批次页面勾选 1～10 件合格板的切件（以
「板号 + 切件序号」标识），设定**正整数目标行长**、**2～4 行**与
**非负整数最小错缝距离**，调用 `POST /api/batches/{id}/joint-preview`。
接口**只读取**冻结切件长度与当前板状态，不写入、不改版本：

* **拒绝（HTTP 400）**：目标行长不是正整数；行数不是 2～4 的整数；错缝距离
  不是非负整数；选件不是 1～10 件的列表；`board_no`、`cut_no` 不是正整数；
  同一（板号, 切件序号）重复选取；板号不属于批次；板为「待加工」或「报废」；
  切件序号超出该板切件数；批次不存在返回 404；
* **拼接规则**：切件长度取批次冻结值；按等宽木条、接头无长度损耗计算，
  不裁短——每行从左至右拼到目标行长，即行内切件长度之和**恰等于**目标行长；
  每件切件最多使用一次，允许余件（选件不必全部用完）；
* **错缝约束**：接缝位置为除末件外的累计长度（单件整行无接缝）；相邻行
  任意两接缝位置差的绝对值须不小于最小错缝距离，无接缝行不限制邻行；
* **精确求解（`joint.py`）**：先用子集 DP 求出「剩余切件拼 k 行」的最少用
  件数作为下界剪枝，再按（板号, 切件号）升序逐件 DFS 拼行，枚举顺序即
  逐行标识序列的字典序，保证：

  1. 用件数最少；
  2. 并列时逐行比较切件标识序列取字典序最小（标识先比板号再比切件号，
     短前缀在前）。
* **响应**：返回目标行长、行数、错缝距离、选件数、用件数、余件数，逐行的
  切件顺序（`rows[].pieces`，含板号、切件号与长度）、接缝坐标
  （`rows[].joints`）与行长，以及未用切件列表（`unused`）；无解时返回
  `feasible=false` 并明确区分「长度组合拼不满所有行」与「错缝约束下
  无可行排布」。

页面在「执行核销」页签的批次详情中提供拼板表单：参数录入、按合格板分组的
切件勾选区（限 10 件，已发料切件禁用并标注）、逐行比例条（段边界即接缝）
与接缝坐标、切件顺序标签及未用切件一览。

## 跨批次合格切件发料

批次存在「合格」原板后，可在「发料单」页签按批次 ID 收集 1～10 件切件
（每件以「批次 ID＋板号＋切件序号」标识，可跨批次），填写**非空用途**与
**非空幂等键**后调用 `POST /api/dispatches`。接口在**一笔 SQLite 事务**
（IMMEDIATE）中核对并冻结：

* **核对**：每件切件所属批次存在、板号属于该批次且已核销为「合格」、
  切件序号不越界、选件在单内不重复，且尚未出现在任何发料单中；
  任一件无效或已发料，**整单不写入**；
* **冻结**：全部有效时把切件长度与归属（批次/板号/切件序号）随发料单
  持久化到 SQLite（`dispatches` + `dispatch_items`），该切件此后不得再
  发料（`dispatch_items` 以（批次, 板号, 切件序号）为主键兜底）；
* **幂等**：幂等键全局唯一；同一幂等键＋同一用途＋同一选件集合的重试
  直接返回首次保存的发料单（选件顺序不影响比较，按批次/板号/切件序号
  排序后规范化）；同键异载荷返回 409；
* **联动**：`GET /api/batches/{id}` 与核销上报响应的每板附带
  `dispatched_cuts`（已发料切件序号列表），批次页标注已发料切件；
  错缝拼板预览拒绝选用已发料切件（HTTP 400）。发料不修改批次版本。

页面「发料单」页签可创建发料单、按 ID 查询发料单，并展示发料明细
（用途、件数、幂等键、创建时间与逐件批次/板号/切件序号/冻结长度）。

## 启动（一条命令）

需要已安装 Docker 与 Docker Compose 插件：

```bash
docker compose up --build
```

启动后浏览器访问：

```
http://localhost:8000
```

数据库文件存放在命名卷 `batch_data`（容器内 `/app/data/batches.db`）中，
首次启动自动初始化，停止或重建容器后批次数据不丢失；如需清空数据可执行
`docker compose down -v`。

停止服务：在当前终端按 `Ctrl+C`；后台运行可用 `docker compose up --build -d`，
停止用 `docker compose down`。

## 本地直接运行（不使用 Docker）

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python app.py
```

同样访问 http://localhost:8000 。端口可通过环境变量 `PORT` 修改；
数据库路径可通过环境变量 `DB_PATH` 修改（默认 `data/batches.db`，启动时自动初始化）。

## 接口说明

### `POST /api/solve` —— 单份清单求解

请求体 JSON：

```json
{
  "board_length": 6000,
  "unit_price": 120,
  "available": 10,
  "kerf": 3,
  "parts": [
    { "length": 2500, "quantity": 2 },
    { "length": 1800, "quantity": 3 },
    { "length": 1200, "quantity": 4 }
  ]
}
```

- 输入不满足约束 → HTTP 400，`{"error": "..."}`；
- 输入合法但无解 → HTTP 200，`{"feasible": false, "reason": "..."}`；
- 成功 → HTTP 200，`{"feasible": true, "boards": [...], "summary": {...}}`。

### `POST /api/allocate` —— 多订单合板费用分摊

请求体 JSON（原板参数与 `/api/solve` 相同，`orders` 为 2～4 个订单）：

```json
{
  "board_length": 6000,
  "unit_price": 120,
  "available": 10,
  "kerf": 3,
  "orders": [
    { "name": "订单A", "parts": [ { "length": 2500, "quantity": 2 }, { "length": 1200, "quantity": 1 } ] },
    { "name": "订单B", "parts": [ { "length": 1800, "quantity": 2 }, { "length": 1200, "quantity": 1 } ] }
  ]
}
```

成功响应（HTTP 200）：

```json
{
  "feasible": true,
  "summary": {
    "order_count": 2,
    "board_count": 2,
    "total_pieces": 6,
    "total_price": 240,
    "total_fen": 24000
  },
  "orders": [
    { "name": "订单A", "share_exact": "180", "pay_fen": 18000 },
    { "name": "订单B", "share_exact": "60", "pay_fen": 6000 }
  ]
}
```

- `share_exact`：该订单的精确分摊值（元），分数形式（如 `"250/3"`），各单之和等于合板最优总价；
- `pay_fen`：最终应付金额（分），按“向下取整 + 小数余数降序补足”取整，
  各单 `pay_fen` 之和等于 `total_fen`；
- 输入不满足约束 → HTTP 400，`{"error": "..."}`；
- 全部订单合板无解 → HTTP 200，`{"feasible": false, "reason": "..."}`，不返回分摊结果。

### `POST /api/schedule` —— 单份清单排料 + 锯机作业排程

请求体 JSON：原板参数与 `/api/solve` 相同，另加统一的 `setup_minutes` 与
`machines`（2～4 台，按录入顺序从 1 编号）：

```json
{
  "board_length": 6000,
  "unit_price": 120,
  "available": 10,
  "kerf": 3,
  "parts": [
    { "length": 2500, "quantity": 2 },
    { "length": 1800, "quantity": 3 },
    { "length": 1200, "quantity": 4 }
  ],
  "setup_minutes": 10,
  "machines": [
    { "ready_minutes": 0, "cut_minutes": 5 },
    { "ready_minutes": 20, "cut_minutes": 3 },
    { "ready_minutes": 5, "cut_minutes": 7 }
  ]
}
```

- `setup_minutes`：统一的每板准备分钟，非负整数；
- `machines[].ready_minutes`：该机最早可用分钟，非负整数；
- `machines[].cut_minutes`：该机每件切割分钟，正整数。

成功响应（HTTP 200）：返回与 `/api/solve` 相同的 `boards`、`summary`，
并附加 `schedule`：

```json
{
  "feasible": true,
  "boards": [ { "board_no": 1, "piece_count": 2, "..." : "..." } ],
  "summary": { "board_count": 3, "..." : "..." },
  "schedule": {
    "machine_count": 3,
    "setup_minutes": 10,
    "makespan": 36,
    "machines": [
      {
        "machine_no": 1,
        "ready_minutes": 0,
        "cut_minutes": 5,
        "job_count": 1,
        "start_minutes": 0,
        "finish_minutes": 30,
        "jobs": [
          { "board_no": 3, "piece_count": 4, "duration_minutes": 30,
            "start_minutes": 0, "finish_minutes": 30 }
        ]
      }
    ]
  }
}
```

- `jobs` 按该机加工顺序（即原板编号升序）给出每块原板的件数、耗时与
  开工/完工分钟；`duration_minutes = setup_minutes + piece_count × cut_minutes`；
- 闲置机台的 `job_count` 为 0，`start_minutes`、`finish_minutes` 为 `null`；
- `makespan` 为**已接单机台**最晚完工分钟的最小值（整体完工分钟），
  即各接单机台 `finish_minutes` 的最大值；闲置机台不计入，其
  `ready_minutes` 再晚也不影响该值；
- 输入不满足约束 → HTTP 400，`{"error": "..."}`；
- 排料无解 → HTTP 200，`{"feasible": false, "reason": "..."}`，不生成排程。

### `POST /api/batches` —— 创建核销批次

请求体与 `/api/solve` 相同（`board_length`、`unit_price`、`available`、`kerf`、
`parts`）。服务端求解，可行时把输入与逐板方案冻结到 SQLite。

- 输入不满足约束 → HTTP 400，`{"error": "..."}`；
- 输入合法但无解 → HTTP 200，`{"feasible": false, "reason": "..."}`，**不建批次**；
- 成功 → HTTP 201，返回冻结快照与初始状态：

```json
{
  "feasible": true,
  "batch_id": 1,
  "version": 0,
  "input": { "board_length": 6000, "unit_price": 120, "available": 10, "kerf": 3,
             "parts": [ { "length": 2500, "quantity": 2 } ] },
  "boards": [ { "board_no": 1, "cuts": [2500, 2500], "status": "pending", "...": "..." } ],
  "summary": { "board_count": 3, "...": "..." }
}
```

各板 `status` 初始为 `pending`（待加工），其余取值为 `qualified`（合格）、
`scrapped`（报废）。

### `GET /api/batches/{id}` —— 查询批次

返回冻结快照、当前版本与逐板状态（含已发料切件）：

```json
{
  "batch_id": 1,
  "version": 2,
  "input": { "...": "..." },
  "boards": [ { "board_no": 1, "cuts": [2500, 2500], "status": "qualified",
                "dispatched_cuts": [1], "...": "..." } ],
  "summary": { "...": "..." }
}
```

- `dispatched_cuts`：该板已发料的切件序号列表（升序），随发料单冻结，
  不得再发料；批次页据此标注，拼板预览拒绝选用。

批次不存在 → HTTP 404，`{"error": "..."}`。

### `POST /api/batches/{id}/reports` —— 上报逐板核销结果

请求体 JSON：

```json
{
  "idem_key": "report-0001",
  "expected_version": 0,
  "results": [
    { "board_no": 1, "result": "qualified" },
    { "board_no": 2, "result": "scrapped" }
  ]
}
```

- `idem_key`：非空字符串幂等键（批次内唯一）；同批次同键同载荷的重试直接返回
  首次保存的响应（忽略期望版本），`results` 列表顺序不影响载荷比较；
- `expected_version`：非负整数，须等于批次当前版本，否则 409；
- `results`：非空逐板结果，`board_no` 须属于本批次且不得重复，`result` 仅可取
  `qualified` / `scrapped`，且每板仅可从「待加工」核销一次。

响应：

- 成功 → HTTP 200，在单个事务中原子更新所有板、版本加一并保存响应，返回
  `{ "batch_id", "version", "updated", "input", "boards", "summary" }`；
- 载荷不合法（空幂等键、空结果、板号不属于批次或重复、结果取值非法等）
  → HTTP 400；
- 批次不存在 → HTTP 404；
- 期望版本过期、上报已核销板、同键异载荷 → HTTP 409，**整批不写入**。

### `POST /api/batches/{id}/quality-preview` —— 批次实测尺寸复核（只读）

请求体 JSON（`measurements` 可为空数组，表示本次没有任何实测件）：

```json
{
  "tolerance": 5,
  "measurements": [
    { "board_no": 1, "cut_no": 1, "actual_length": 2502 },
    { "board_no": 1, "cut_no": 2, "actual_length": 2498 }
  ]
}
```

- `tolerance`：非负整数；`measurements[]` 的 `board_no`、`cut_no`（从 1 开始）
  与 `actual_length`（正整数）均为整数，同一（板号, 切件序号）不得重复，
  板必须属于本批次且当前状态为 `qualified`，切件序号不得超出该板切件数；
  待加工、报废板的记录或重复切件一律 400；批次不存在 → 404；
- 接口只读：读取冻结需求与当前板状态，**不修改批次、版本与核销记录**。

成功响应（HTTP 200）：

```json
{
  "batch_id": 1,
  "tolerance": 5,
  "demand_count": 4,
  "measured_count": 2,
  "matched_count": 2,
  "unassigned_count": 0,
  "total_deviation": 4,
  "demands": [ { "demand_no": 1, "length": 2500 } ],
  "assignments": [
    { "board_no": 1, "cut_no": 1, "planned_length": 2500,
      "actual_length": 2502, "assigned": true,
      "demand_no": 1, "demand_length": 2500, "deviation": 2 },
    { "board_no": 1, "cut_no": 2, "planned_length": 2500,
      "actual_length": 2498, "assigned": false,
      "demand_no": null, "demand_length": null, "deviation": null }
  ],
  "unassigned": [ { "board_no": 1, "cut_no": 2, "..." : "..." } ],
  "shortages": [
    { "length": 2500, "required": 2, "matched": 1, "shortage": 1 }
  ]
}
```

- `assignments` 按（板号, 切件序号）排列，即字典序比较时实测件的固定顺序；
- 匹配目标依次为满足件数最多、总长度偏差最小、需求件序号序列字典序最小
  （未分配排在最后）；`unassigned` 为 `assigned=false` 的实测件；
- `shortages` 按冻结零件录入顺序逐种长度给出需求件数、已满足件数与缺件数。

### `POST /api/batches/{id}/joint-preview` —— 合格切件错缝拼板预览（只读）

请求体 JSON：

```json
{
  "pieces": [
    { "board_no": 1, "cut_no": 1 },
    { "board_no": 1, "cut_no": 2 },
    { "board_no": 2, "cut_no": 1 }
  ],
  "target_length": 6000,
  "row_count": 2,
  "min_stagger": 300
}
```

- `pieces`：1～10 件选件，以（板号, 切件序号）标识，不得重复；板须属于本
  批次且当前状态为 `qualified`，切件序号不得越界，且切件未发料（已发料
  切件出现在 `dispatched_cuts` 中，选用即 400）；切件长度取批次冻结值；
- `target_length`：正整数目标行长；`row_count`：2～4 的整数；
  `min_stagger`：非负整数（允许 0，即不限制错缝）；
- 输入不满足约束 → HTTP 400，`{"error": "..."}`；批次不存在 → HTTP 404；
- 接口只读：**不修改批次、版本与核销记录**。

成功响应（HTTP 200）：

```json
{
  "batch_id": 1,
  "feasible": true,
  "target_length": 6000,
  "row_count": 2,
  "min_stagger": 300,
  "selected_count": 3,
  "used_count": 3,
  "unused_count": 0,
  "rows": [
    {
      "row_no": 1,
      "piece_count": 2,
      "total_length": 6000,
      "pieces": [
        { "board_no": 1, "cut_no": 1, "length": 2500 },
        { "board_no": 2, "cut_no": 1, "length": 3500 }
      ],
      "joints": [2500]
    },
    {
      "row_no": 2,
      "piece_count": 1,
      "total_length": 6000,
      "pieces": [
        { "board_no": 1, "cut_no": 2, "length": 6000 }
      ],
      "joints": []
    }
  ],
  "unused": []
}
```

- 每行切件长度之和恰等于目标行长（等宽木条、接头无损耗、不裁短），每件
  最多用一次，允许余件；`joints` 为除末件外的累计长度（单件整行为空数组）；
- 相邻行任意两接缝位置差的绝对值不小于 `min_stagger`，无接缝行不限制邻行；
- 排布**用件数最少**；并列时逐行比较（板号, 切件号）标识序列取字典序最小，
  短前缀在前；
- 无解 → HTTP 200，`{"feasible": false, "reason": "..."}`，明确区分
  「长度组合拼不满所有行」与「错缝约束下无可行排布」。

### `POST /api/dispatches` —— 创建跨批次发料单

请求体 JSON：

```json
{
  "idem_key": "dsp-0001",
  "purpose": "三号线框架用料",
  "pieces": [
    { "batch_id": 1, "board_no": 1, "cut_no": 1 },
    { "batch_id": 2, "board_no": 3, "cut_no": 2 }
  ]
}
```

- `idem_key`：非空字符串幂等键（全局唯一）；同一幂等键＋同一用途＋同一
  选件集合的重试直接返回首次保存的发料单，`pieces` 列表顺序不影响载荷比较；
- `purpose`：非空字符串用途；
- `pieces`：1～10 件选件，以（批次 ID, 板号, 切件序号）标识，单内不得重复；
  每件所属批次须存在、板号属于该批次且当前状态为 `qualified`、切件序号
  不越界，且尚未出现在任何发料单中。

响应：

- 成功 → HTTP 201，在一笔 SQLite 事务中冻结切件长度与归属并持久化发料单，
  返回发料单明细（见下）；同键同载荷的幂等重试 → HTTP 200，返回首次保存的
  同一发料单；
- 载荷不合法（空幂等键/用途、选件数量越界、切件重复、批次不存在、板号
  不属于批次或未核销合格、切件序号越界等）→ HTTP 400，**整单不写入**；
- 同键异载荷、选件含已发料切件 → HTTP 409，**整单不写入**。

成功响应（HTTP 201）：

```json
{
  "dispatch_id": 1,
  "idem_key": "dsp-0001",
  "purpose": "三号线框架用料",
  "piece_count": 2,
  "created_at": "2026-09-27 08:00:00",
  "pieces": [
    { "batch_id": 1, "board_no": 1, "cut_no": 1, "length": 2500 },
    { "batch_id": 2, "board_no": 3, "cut_no": 2, "length": 1800 }
  ]
}
```

- `pieces` 按（批次 ID, 板号, 切件序号）排列，`length` 为发料时冻结的
  切件长度；切件归属（批次/板号/切件序号）随发料单一并冻结，不得再发料。

### `GET /api/dispatches/{id}` —— 查询发料单

返回持久化的发料单明细（字段与创建响应相同）；发料单不存在 → HTTP 404，
`{"error": "..."}`。

├── static/
│   ├── index.html      # 页面
│   ├── style.css       # 样式
│   └── app.js          # 原生 JavaScript 交互
├── Dockerfile
├── docker-compose.yml
└── requirements.txt
